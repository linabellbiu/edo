# ZRT 架构说明

## 运行组件

ZRT 由同一个 Go 二进制和一个 Vue 静态站点组成：

- `zrt migrate`：显式执行数据库结构迁移。
- `zrt server`：在一个 Go 进程内提供 Gin API、Vue 静态资源与 WebSocket 终端，并通过 Goroutine 消费 NATS JetStream 任务、投递 Outbox、运行监控与定时调度扫描器。
- `web/`：Vue 3、TypeScript、Vite、Vue Router、Pinia 和 Ant Design Vue 前端，应用外壳与交互遵循 Vben Admin 5 `web-antd` 基线。

ZRT 主进程中的 HTTP 与后台协程共享数据库、Redis、NATS 和同一份 `ZRT_SECRETS_KEY`。任一关键后台协程异常退出都会使主进程安全退出，由容器编排系统整体重启，避免出现 API 正常但任务停止的半失效状态。服务启动只验证迁移版本，不会静默修改生产表结构。

## 数据库

默认 SQLite 适合单机和试用；运行多个 ZRT 实例时应使用 PostgreSQL 或 MySQL。SQLite 固定单连接并启用 WAL、外键和 busy timeout，不应通过网络文件系统在多主机间共享数据库文件。

所有模型通过同一组版本化 GORM 迁移在 SQLite、PostgreSQL、MySQL 上创建。CI 使用实际 PostgreSQL 和 MySQL 服务重复执行迁移，以验证幂等性。

## Redis 的职责

Redis 保留用于：

- 不透明登录会话；Redis 只保存会话 Token 的 SHA-256 摘要。
- 登录失败锁定和有过期时间的短期状态。登录锁定默认关闭，只有管理员在系统设置中显式开启后才累计失败次数；切换开关会清理旧计数，不影响现有会话。
- 后续横向扩容时的分布式锁、发布并发协调与实时状态。

Redis 不再用 List 充当任务队列。项目使用 go-redis/v9；这里的 v9 是 Go 客户端主版本，不代表 Redis Server 9。客户端固定 RESP2，当前部署基线为 Redis Server 7.x。

## NATS 与有限重试

任务记录和 Outbox 事件在一个数据库事务中创建。进程内 Publisher 使用 JetStream 消息 ID 去重后投递，后台任务协程显式 Ack、Nak 或 Term。

- `max_attempts` 包含首次执行，默认值为 4，即最多重试 3 次。
- 临时网络故障、超时和限流按退避策略重试。
- 参数、权限、签名和配置错误立即终止。
- 发布和回滚存在外部副作用，默认最大执行次数为 1。
- 执行次数耗尽后写入死信 Stream，并保存稳定的中文失败提示。
- Outbox 自身也使用有限投递次数，不能无限重试。

任务 Stream 默认上限为 512 MiB，死信 Stream 为 256 MiB，可通过 `ZRT_NATS_MAX_BYTES` 和 `ZRT_NATS_DEAD_MAX_BYTES` 按磁盘容量调整。ZRT 不再写死会导致小磁盘 JetStream 拒绝启动的 10GB 预留值。

## WebSocket 的用途

交互式终端需要双向、低延迟、持续传输二进制输出和终端尺寸变更，因此保留 WebSocket。SSE 只有服务端到浏览器的单向流，不能自然承载键盘输入和 resize 控制，不能替代交互终端。

WebSocket 用于 Docker 容器和 Kubernetes Pod Exec，也承载只读的 Docker 容器实时日志。宿主机 SSH、宿主机文件管理和浏览器直连服务器已删除。HTTP API 与终端 WebSocket 不限制 Origin、Host 或 Sec-Fetch-Site，跨来源访问仍必须通过登录会话、权限和专用子协议校验，并限制帧大小、写入时间及最长会话时长；终端和容器日志打开、关闭都会写审计日志。Docker 日志直接调用 daemon 的 `ContainerLogs`，非 TTY 输出在服务端解复用 stdout/stderr；运行中容器可以持续跟随，重启中和已停止容器仍可查看受限行数的最近输出，不会通过 SSH 执行任意命令。

## 发布边界

- Docker 通过受控 Unix Socket 或双向 TLS Docker API 连接，拒绝明文远程 TCP API。
- Kubernetes 使用 in-cluster 身份或加密保存的 kubeconfig，拒绝 exec 插件和外部文件引用。
- 通过镜像仓库或 Kubernetes 发布时统一使用镜像摘要；本地或 SSH 传输的 Docker 镜像使用真实 Image ID 校验。环境名称或分组不改变制品校验强度。是否审核仅由流水线阶段中的审核任务决定，不提供应用或环境级审核开关。
- 发布任务保存目标快照；之后修改目标不会改变已经排队的任务。
- 新实例必须通过 Docker 健康状态或 Kubernetes Rollout 检查，失败时记录需人工确认的安全提示。
- Docker/Pod 终端不提供宿主机逃逸能力；实际权限仍由 Docker Socket 边界和 Kubernetes RBAC 决定。

## Git 与凭据

仓库类型支持 generic、GitHub、GitLab、Gitea、Gitee。每个用户都有独立的 Git 令牌库，列表、修改、删除和明文查看都按所有者隔离；即使是超级管理员，也不能通过令牌接口读取其他用户保存的密钥。密钥使用 AES-256-GCM 加密，普通列表只返回掩码提示，查看原文需要显式操作并写入审计日志。

创建仓库时可以选择当前用户已经保存的令牌，也可以在仓库表单中创建并保存新令牌。仓库只保存令牌引用，执行 Git 操作时才由后端解析密文；不能引用其他用户的令牌。HTTPS Token 和 SSH 私钥均支持该模式，SSH 仍强制使用可信 `known_hosts`，不会关闭主机指纹校验。

Webhook 按平台校验签名并经过 Transactional Outbox 进入任务队列。Webhook 签名密钥不是一次性数据：拥有 `repository.secret.read` 权限的用户可再次查看，查看动作会写审计日志，响应禁止浏览器和代理缓存。

外部 Git Webhook API 另设全局安全开关，默认关闭，由拥有 `config.manage` 权限的管理员在“系统设置”中开启。全局开关只控制公网接收入口，不替代仓库自身的 Webhook 开关和签名密钥；数据库无法读取全局开关时按关闭处理。支持的常见事件为分支 Push、Tag Push 和 PR/MR，未知事件安全忽略。此次调整会改变升级后外部请求的默认行为：原有仓库配置、密钥和投递历史不迁移、不删除，但管理员必须显式开启全局开关后，已有 Webhook 才会继续接收。首次保存开关时复用配置中心及修订记录，不增加影子配置表。

## RBAC 权限模型

ZRT 的有效权限由角色权限和用户级权限例外共同计算。角色用于批量授予功能权限；用户例外支持“额外允许”和“显式拒绝”，显式拒绝优先于角色或用户允许。超级管理员拥有全部权限，但个人 Git 令牌仍遵守所有者隔离，避免管理员权限变成跨用户密钥读取能力。

前端菜单、页面操作和后端接口使用同一份有效权限。前端隐藏功能只用于改善使用体验，真正的授权判断始终由后端在每次请求时通过 Casbin 执行。GORM 的角色权限、用户角色和用户权限覆盖表是唯一事务数据源，只读适配器将其加载到 Casbin；Redis Watcher 在多实例间广播策略变更。用户、角色、权限例外和密钥查看等变更都会进入审计记录。

## 域名与 DNS 解析

域名模块管理已有权威 DNS Zone 和解析记录，不承担域名购买、续费、过户或注册商账户管理。删除 ZRT 中的域名只删除本地引用，不会删除厂商侧 Zone；删除解析记录则会立即改变外部 DNS 状态，因此必须拥有 `dns.manage` 权限并经过明确确认。读取权限使用 `dns.read`。

厂商驱动统一使用相对主机记录、记录类型、标准 RDATA 和 TTL 模型，当前静态集成 Cloudflare、阿里云 DNS、腾讯云 DNSPod、AWS Route 53、华为云 DNS、Azure DNS、Google Cloud DNS、DigitalOcean、Gandi LiveDNS、GoDaddy、Namecheap、Hetzner DNS、PowerDNS 和 RFC 2136/TSIG。驱动层与业务层分离，新增厂商不需要改动域名、记录、权限或审计逻辑。各厂商对记录类型、TTL 下限和高级路由策略的支持仍以其 API 为准；ZRT 当前只统一普通权威记录，不把 Route 53 加权路由、Cloudflare 负载均衡等厂商专属对象伪装成普通记录。

公开配置和敏感字段分列保存，AccessKey、Token、服务账号 JSON、TSIG Secret 等统一使用 `ZRT_SECRETS_KEY` 加密；列表接口只返回已配置字段名，不返回密文或明文。记录操作直接调用厂商 API，ZRT 不会通过任务队列自动重投，避免超时后的消息重投重复创建外部记录。同一域名的读取和写入在单进程内串行化；修改单条记录时保留同名同类型 RRset 的其他成员，并按厂商驱动能力选择完整 RRset 替换、记录 ID 更新或带补偿恢复的精确替换。若驱动只能覆盖或删除整个 RRset，ZRT 会拒绝对多值记录集执行单条新增、修改或删除，要求在厂商控制台处理，避免误伤同组记录。SOA 与根域名 NS 记录在 ZRT 中只读，防止误操作破坏权威 Zone。

## 持续交付流程

应用只负责关联一个代码仓库和一条流水线。代码仓库只保存 Git 来源、个人令牌引用和可选 Webhook；构建方案、镜像仓库和部署方案不再绑定到应用，而是由流水线中的具体任务选择。多个应用之间的并行、串行、依赖和失败策略仍放在发布计划的发布组中。

流水线采用类似 Gitee 的受约束图形结构：左侧是唯一代码源，右侧按执行顺序横向分栏，每个阶段内使用从左到右的任务链。阶段边界及任务之间提供“＋”插入入口，点击阶段或任务后在右侧抽屉编辑；任务库按构建、测试、扫描、发布、部署和工具分类。系统不提供自由连线、节点坐标、缩放或无限画布。前后端直接保存版本化的 `source + stages[].tasks[]` 结构，后端再次验证必须恰有一个代码源、至少一个阶段且每个阶段至少一个任务。

流水线方案保存时使用修订号防止并发覆盖。应用引用方案时跟随其最新已启用版本，方案草稿不影响应用；直接编辑应用流水线会解除方案关联并转为自定义配置。每次运行保存启动时的代码源、阶段、任务、构建方案、制品、部署方案和内部目标快照，后续配置修改不能篡改在途运行。

唯一代码源保存 Push、Pull Request、Tag 监听条件以及是否允许人工选择版本启动。手动启动不是独立任务，服务端会重新解析所选分支或 Tag 并固定 Commit，然后与自动事件复用同一条任务链。ZRT 后台按检查间隔主动读取远程 Git 引用和托管平台 PR/MR；事件与具体 Ref 分别保存监听游标，新应用首次检查只建立基线，之后的 Commit、新分支、新 PR/MR 或新 Tag 会自动创建运行。Webhook 只是可选的低延迟入口；流水线未启用时不使用应用表单中的旧触发配置兜底。

构建任务显式选择构建方案。Dockerfile 方案提供开箱即用默认值：工作目录和构建上下文为 `.`、Dockerfile 为 `Dockerfile`、超时 1800 秒、启用拉取基础镜像和本地层缓存；高级参数包括目标阶段、平台、Docker 构建参数和可选镜像仓库。应用运行时环境变量属于部署方案，不伪装成 Dockerfile 构建输入。脚本方案另外支持构建容器环境变量，并在隔离容器中使用固定非交互 `sh -se`；运行镜像默认 `alpine:3.22`，镜像必须提供 `/bin/sh`，只接受带明确非 `latest` Tag 或 Digest 的 OCI 引用。脚本方案必须声明产物路径，目录产物由 ZRT 确定性打包为 `tar.gz`，普通文件保持原格式，不向用户暴露多余的打包格式字段。构建始终从已固定 Commit 的独立检出目录执行，结束后登记 SHA-256 可验证的不可变制品；手工上传制品与构建方案位于同一入口，上传也执行大小限制、摘要计算和原子存储。

Dockerfile 构建输出 OCI 镜像制品：未选镜像仓库时登记构建 daemon 中的镜像 ID，选择仓库时由构建运行时推送并登记不可变 Digest。脚本构建输出文件制品，由 ZRT 打包并存入受控制品目录。Compose 使用隔离的 Docker-in-Docker/BuildKit 和持久层缓存，本地二进制复用宿主机 Docker；构建不得占用远程发布主机。绑定仓库时维护 `zrt-cache` 标签作为可丢失缓存，缓存失败只记录告警，不改变正式制品结果。

部署方案把“怎么执行”和“部署到哪里”一次保存完整，内部唯一解析环境、主机或运行时、工作目录、容器名称、命名空间和工作负载。流水线部署任务只选择一个部署方案并消费上游制品，不得填写 Dockerfile、构建上下文、独立环境或发布目标，也不得重新检出和构建源码。主机脚本只接受文件制品；本地或远程 Docker 接受 OCI 镜像，本地直接校验同一 daemon，远程无仓库时通过 SSH 执行受限的 `docker load`，有仓库时拉取 Digest；Docker Compose 使用表单内联 YAML 并由 ZRT 注入上游镜像，不从仓库读取 Compose 文件或再次构建；Kubernetes Deployment 必须使用集群可拉取的仓库 Digest。当前不对外宣称 Helm 部署，因为未实现真实 Helm 执行器。部署任务默认只投递一次，只有真实发布记录成功后流水线才能成功。

NATS Consumer 后使用固定大小的 Worker 池，`ZRT_WORKER_CONCURRENCY` 是真实并发执行上限。每个 Docker 构建使用独立检出目录、上下文、临时认证目录和标签，可并行调用 Buildx，不使用全局构建锁；只有更新同一发布目标时使用分布式锁。Dockerfile 构建对明确的临时网络错误可有限重试，脚本和 Shell 默认只执行一次，参数、权限、路径和配置错误立即失败。

## 内置系统监控

拥有 `monitor.read` 权限的用户可以从“系统监控”页面直接查看 ZRT 所在节点与进程的 CPU、内存和负载，Go 堆、Goroutine 与 GC，Worker 实例、并发容量和当前执行数量，以及任务状态、Outbox、JetStream 积压、待确认、重投、死信和数据库连接池。页面通过受登录和权限保护的 `/api/v1/system/metrics` 每 5 秒刷新；最近趋势只保留在当前浏览器页面内，不写入数据库。

主机与进程数据由 `gopsutil/v4` 读取，Go 运行时数据使用标准库，JetStream 状态使用现有 NATS 官方客户端。任一采集源异常时，接口仍返回其他可用指标，同时记录包含组件名和原始错误的服务端日志；对外只显示不可用的指标名称。Grafana、Prometheus 或独立采集 Agent 都不是使用内置页面的前置条件。

失败运行可以从页面重新执行。ZRT 不修改原失败记录，而是使用原 Git Ref 和 Commit、新建运行与 NATS 任务，并通过 `retry_of_id` 保留审计链。重新执行读取当前任务引用的有效构建方案、部署方案和流水线配置，生成新的制品和运行快照；审核结果不会复用，必须在新运行中重新完成。

发布计划内部创建发布组。一个发布组选择多个应用并配置组内并行或串行、失败即停止或记录失败后继续；发布组之间可以建立前置依赖，服务端拒绝循环依赖。创建计划不要求用户命名或编写版本号，只填写说明，服务端生成不展示的内部标识。发布计划、流水线运行和发布记录在同一页面通过页内标签切换；发布记录是不可编辑的审计结果。

基础设施资源分为环境、主机、运行时和内部发布目标四层。`environments` 是用户自定义的主机分组，不携带开发、预发布、生产等安全级别；`hosts` 保存 SSH 连接和可用能力；Docker Endpoint 与 Kubernetes Cluster 表示真实运行时。`deployment_targets` 只作为部署方案内部的一对一执行参数存在，不在流水线任务或常规导航中单独选择和保存。用户创建部署方案时在一个表单内同时配置执行方式与实际位置，接口用一次事务保存方案及内部目标并回传真实关联。

内置本地主机默认名称为“本地”，不可删除或停用，但可编辑名称与本地 Docker、直接执行等能力；用户关闭能力后不得被启动或迁移静默恢复。是否可用由官方 Moby 客户端实际连接当前构建运行时确认：Compose 使用隔离的 Docker-in-Docker，宿主机二进制使用本地 Docker daemon，Windows 遵循 Docker 标准环境与 npipe 配置。Docker 未安装或不可达时该能力与相关部署方案置为不可用，readiness 在数据库、Redis 和 NATS 正常时返回降级而不是不健康。

“本地直接执行”不是宿主机 Web 终端；它只允许流水线使用固定的非交互式 `sh` 入口执行已保存的脚本快照，并继续受脚本体积、超时、日志归档和审计约束。Linux 容器内的 Compose 运行以及存在 `sh` 的 Linux/macOS 二进制可以开启，Windows 原生二进制不支持。远程主机编辑默认在服务端复用已加密 SSH 凭据完成必要的真实重测，用户只在明确替换凭据时需要重新输入密码或私钥。

本轮流水线重构不迁移旧自由画布和旧节点定义，也不保留旧结构的解析或执行兜底。迁移 `202607300043` 会删除并重建 `release_workflows`、`release_workflow_templates`，同时清空应用的流水线方案关联；升级后必须使用阶段式编辑器重新配置并启用流水线。已有 `pipeline_runs`、运行日志及关联审计记录不会删除，但旧快照只作为原始审计数据保留，不能展示新拓扑、重新执行或继续推进。新的流水线定义和运行快照都要求精确的结构版本。制品正文默认写入 `ZRT_ARTIFACTS_DIRECTORY`，默认单文件上限由 `ZRT_ARTIFACTS_MAX_BYTES` 控制，数据库只保存元数据、摘要和存储引用。

## 错误与审计

数据库、Redis、NATS、网络地址、调用栈和原始依赖错误只进入结构化日志。HTTP 客户端只收到稳定、可展示的中文错误和请求 ID。身份、角色、仓库、集群、发布、配置、通知、监控、调度、任务与终端操作均受 RBAC 控制并写入审计记录。

## 企业登录

ZRT 保留本地账户登录，同时支持 LDAP、通用 OAuth、飞书、Google、GitHub 和 GitLab。登录方式集中在“系统设置 → 登录方式”中管理，并继续使用独立的身份读取和管理权限；客户端密钥和 LDAP 查询密码使用 `ZRT_SECRETS_KEY` 加密，接口只返回“已配置”，不会回显原文。

- LDAP 先用只读服务账号查找唯一用户，再使用该用户的 DN 和密码重新绑定；默认要求 LDAPS 或 StartTLS。明文 LDAP 只有管理员明确勾选后才允许。
- OAuth 授权请求使用一次性 state 和 PKCE，状态保存在 Redis 中并在回调时原子消费，十分钟后自动过期。回调地址来自管理员保存的配置，不信任请求的 Host 头。
- 外部身份只按“登录方式 + 外部唯一 ID”绑定。ZRT 不会因为邮箱相同自动合并本地账户，避免可伪造邮箱造成账号冒领。
- 管理员可以允许首次登录自动创建普通用户，并选择一个默认角色；未选择角色时，新用户可以登录但没有业务权限。外部登录不会创建超级管理员。
- 停用登录方式会立即阻止新的登录请求，但不会强制中断已经建立的会话；需要立即收回访问时，应同时停用对应用户。

迁移新增 `identity_providers` 和 `external_identities` 两张表，不修改已有用户、密码或角色。升级后所有外部登录方式默认不存在，本地管理员登录行为保持不变；管理员配置并启用某个登录方式后，它才会出现在登录页。
