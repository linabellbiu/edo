# ZRT 架构说明

## 运行组件

ZRT 由同一个 Go 二进制和一个 React 静态站点组成：

- `zrt migrate`：显式执行数据库结构迁移。
- `zrt server`：在一个 Go 进程内提供 Gin API、React 静态资源与 WebSocket 终端，并通过 Goroutine 消费 NATS JetStream 任务、投递 Outbox、运行监控与定时调度扫描器。
- `web/`：React 19、TypeScript 和 Vite 前端。

ZRT 主进程中的 HTTP 与后台协程共享数据库、Redis、NATS 和同一份 `ZRT_SECRETS_KEY`。任一关键后台协程异常退出都会使主进程安全退出，由容器编排系统整体重启，避免出现 API 正常但任务停止的半失效状态。服务启动只验证迁移版本，不会静默修改生产表结构。

## 数据库

默认 SQLite 适合单机和试用；运行多个 ZRT 实例时应使用 PostgreSQL 或 MySQL。SQLite 固定单连接并启用 WAL、外键和 busy timeout，不应通过网络文件系统在多主机间共享数据库文件。

所有模型通过同一组版本化 GORM 迁移在 SQLite、PostgreSQL、MySQL 上创建。CI 使用实际 PostgreSQL 和 MySQL 服务重复执行迁移，以验证幂等性。

## Redis 的职责

Redis 保留用于：

- 不透明登录会话；Redis 只保存会话 Token 的 SHA-256 摘要。
- 登录失败锁定和有过期时间的短期状态。登录锁定默认关闭，只有管理员在系统设置中显式开启后才累计失败次数；切换开关会清理旧计数，不影响现有会话。
- 后续横向扩容时的分布式锁、发布并发协调与实时状态。

Redis 不再用 List 充当任务队列。项目使用 go-redis/v9；这里的 v9 是 Go 客户端主版本，不代表 Redis Server 9。客户端固定 RESP2，当前部署基线为 Redis Server 7.x。

## NATS 与有限重试

任务记录和 Outbox 事件在一个数据库事务中创建。进程内 Publisher 使用 JetStream 消息 ID 去重后投递，后台任务协程显式 Ack、Nak 或 Term。

- `max_attempts` 包含首次执行，默认值为 4，即最多重试 3 次。
- 临时网络故障、超时和限流按退避策略重试。
- 参数、权限、签名和配置错误立即终止。
- 发布和回滚存在外部副作用，默认最大执行次数为 1。
- 执行次数耗尽后写入死信 Stream，并保存稳定的中文失败提示。
- Outbox 自身也使用有限投递次数，不能无限重试。

任务 Stream 默认上限为 512 MiB，死信 Stream 为 256 MiB，可通过 `ZRT_NATS_MAX_BYTES` 和 `ZRT_NATS_DEAD_MAX_BYTES` 按磁盘容量调整。ZRT 不再写死会导致小磁盘 JetStream 拒绝启动的 10GB 预留值。

## WebSocket 的用途

交互式终端需要双向、低延迟、持续传输二进制输出和终端尺寸变更，因此保留 WebSocket。SSE 只有服务端到浏览器的单向流，不能自然承载键盘输入和 resize 控制，不能替代交互终端。

WebSocket 仅用于 Docker 容器和 Kubernetes Pod Exec。宿主机 SSH、宿主机文件管理和浏览器直连服务器已删除。HTTP API 与终端 WebSocket 不限制 Origin、Host 或 Sec-Fetch-Site，跨来源访问仍必须通过登录会话、`terminal.open` 权限和 `zrt-terminal-v1` 子协议校验，并限制帧大小、写入时间及最长会话时长；打开和关闭都会写审计日志。

## 发布边界

- Docker 通过受控 Unix Socket 或双向 TLS Docker API 连接，拒绝明文远程 TCP API。
- Kubernetes 使用 in-cluster 身份或加密保存的 kubeconfig，拒绝 exec 插件和外部文件引用。
- 直接发起的生产发布必须使用镜像摘要，并由非申请人审批。发布审核可按应用开启或关闭；开启后，该应用生成的流水线运行必须经过审核，所有到达生产部署节点的路径都必须包含审核节点。
- 发布任务保存目标快照；之后修改目标不会改变已经排队的任务。
- 新实例必须通过 Docker 健康状态或 Kubernetes Rollout 检查，失败时记录需人工确认的安全提示。
- Docker/Pod 终端不提供宿主机逃逸能力；实际权限仍由 Docker Socket 边界和 Kubernetes RBAC 决定。

## Git 与凭据

仓库类型支持 generic、GitHub、GitLab、Gitea、Gitee。每个用户都有独立的 Git 令牌库，列表、修改、删除和明文查看都按所有者隔离；即使是超级管理员，也不能通过令牌接口读取其他用户保存的密钥。密钥使用 AES-256-GCM 加密，普通列表只返回掩码提示，查看原文需要显式操作并写入审计日志。

创建仓库时可以选择当前用户已经保存的令牌，也可以在仓库表单中创建并保存新令牌。仓库只保存令牌引用，执行 Git 操作时才由后端解析密文；不能引用其他用户的令牌。HTTPS Token 和 SSH 私钥均支持该模式，SSH 仍强制使用可信 `known_hosts`，不会关闭主机指纹校验。

Webhook 按平台校验签名并经过 Transactional Outbox 进入任务队列。Webhook 签名密钥不是一次性数据：拥有 `repository.secret.read` 权限的用户可再次查看，查看动作会写审计日志，响应禁止浏览器和代理缓存。

外部 Git Webhook API 另设全局安全开关，默认关闭，由拥有 `config.manage` 权限的管理员在“系统设置”中开启。全局开关只控制公网接收入口，不替代仓库自身的 Webhook 开关和签名密钥；数据库无法读取全局开关时按关闭处理。支持的常见事件为分支 Push、Tag Push 和 PR/MR，未知事件安全忽略。此次调整会改变升级后外部请求的默认行为：原有仓库配置、密钥和投递历史不迁移、不删除，但管理员必须显式开启全局开关后，已有 Webhook 才会继续接收。首次保存开关时复用配置中心及修订记录，不增加影子配置表。

## RBAC 权限模型

ZRT 的有效权限由角色权限和用户级权限例外共同计算。角色用于批量授予功能权限；用户例外支持“额外允许”和“显式拒绝”，显式拒绝优先于角色或用户允许。超级管理员拥有全部权限，但个人 Git 令牌仍遵守所有者隔离，避免管理员权限变成跨用户密钥读取能力。

前端菜单、页面操作和后端接口使用同一份有效权限。前端隐藏功能只用于改善使用体验，真正的授权判断始终由后端在每次请求时通过 Casbin 执行。GORM 的角色权限、用户角色和用户权限覆盖表是唯一事务数据源，只读适配器将其加载到 Casbin；Redis Watcher 在多实例间广播策略变更。用户、角色、权限例外和密钥查看等变更都会进入审计记录。

## 域名与 DNS 解析

域名模块管理已有权威 DNS Zone 和解析记录，不承担域名购买、续费、过户或注册商账户管理。删除 ZRT 中的域名只删除本地引用，不会删除厂商侧 Zone；删除解析记录则会立即改变外部 DNS 状态，因此必须拥有 `dns.manage` 权限并经过明确确认。读取权限使用 `dns.read`。

厂商驱动统一使用相对主机记录、记录类型、标准 RDATA 和 TTL 模型，当前静态集成 Cloudflare、阿里云 DNS、腾讯云 DNSPod、AWS Route 53、华为云 DNS、Azure DNS、Google Cloud DNS、DigitalOcean、Gandi LiveDNS、GoDaddy、Namecheap、Hetzner DNS、PowerDNS 和 RFC 2136/TSIG。驱动层与业务层分离，新增厂商不需要改动域名、记录、权限或审计逻辑。各厂商对记录类型、TTL 下限和高级路由策略的支持仍以其 API 为准；ZRT 当前只统一普通权威记录，不把 Route 53 加权路由、Cloudflare 负载均衡等厂商专属对象伪装成普通记录。

公开配置和敏感字段分列保存，AccessKey、Token、服务账号 JSON、TSIG Secret 等统一使用 `ZRT_SECRETS_KEY` 加密；列表接口只返回已配置字段名，不返回密文或明文。记录操作直接调用厂商 API，ZRT 不会通过任务队列自动重投，避免超时后的消息重投重复创建外部记录。同一域名的读取和写入在单进程内串行化；修改单条记录时保留同名同类型 RRset 的其他成员，并按厂商驱动能力选择完整 RRset 替换、记录 ID 更新或带补偿恢复的精确替换。若驱动只能覆盖或删除整个 RRset，ZRT 会拒绝对多值记录集执行单条新增、修改或删除，要求在厂商控制台处理，避免误伤同组记录。SOA 与根域名 NS 记录在 ZRT 中只读，防止误操作破坏权威 Zone。

## 持续交付流程

应用是构建和部署的配置边界，一个应用只对应一个代码仓库，并分别配置 dev、test、pre、prod 环境；环境可以少选，例如只保留 test 和 prod。代码仓库只负责 Git 来源、个人令牌引用和 Webhook。应用统一选择构建方案、部署方案、可选镜像仓库、流水线和审核策略。每个环境保存监听分支以及 Pull、Push、PR、Tag 规则。多个应用之间的并行、串行、依赖和失败策略统一放在发布计划的发布组中，应用自身不提供仓库排序、顺序发布或无序发布配置。

“部署方案”“流水线方案”“流水线运行”和“发布计划”是四个不同概念。部署方案是应用可复用的 Helm、Compose、Docker 或脚本执行模板，回答应用“如何部署”；流水线方案是可被多个应用选择的公共环境流转图，回答代码事件“按什么路径流转到各环境”；流水线运行是一次由代码事件或手动操作触发的具体执行，保存代码版本、方案快照、审核要求和执行状态；发布计划则表示一次迭代、版本或发布列车，例如 `2026.08`。流水线方案菜单先展示名称、状态、版本、节点规模、使用应用和更新时间列表，再进入类似 ComfyUI 的无限画布编辑。环境、分支、Pull/Push/PR/Tag、人工接测、审核和部署节点作为节点参数配置，连线表达允许的晋级方向。图必须是无环结构，不能有悬空的非触发节点，最后一个节点必须是部署节点。未被应用或应用流水线引用的方案可以删除，仍在使用的方案必须先解除引用。

流水线方案保存时使用修订号进行并发检查，避免两个管理员互相覆盖。创建应用时选择一份已启用的方案，系统复制完整节点、连线和环境参数成为应用流水线，并记录来源方案及修订号；公共方案后续更新不会静默改写现有应用。应用仍可在自己的画布中二次调整。每次流水线运行保存启动时的应用流水线、构建方案和部署方案快照，因此应用配置之后发生修改，已经开始的运行仍按原快照推进。发布审核开关保存在应用上，并在创建流水线运行时写入快照；每个审核节点单独保存审核记录，申请人不能审核自己。

Pull 监听在每个环境首次检查时只建立代码基线，不会把已有提交误判成新版本；之后提交发生变化才创建流水线运行。Push、PR 与 Tag 由经过签名校验和去重的仓库 Webhook 驱动，并按已启用应用流水线中的触发节点过滤。应用流水线尚未启用时，系统继续使用应用表单中的环境触发配置，便于先建立代码基线。

应用流水线负责代码触发、环境晋级、人工放行、审核和部署执行；流水线运行记录一次具体执行。手动执行时为应用的代码仓库选择一个 Commit，运行会保存仓库、Commit，以及应用的构建方案、可选镜像仓库和部署方案快照。到达部署节点后，ZRT 创建最大执行次数为 1 的 `pipeline.deploy` NATS 任务并使用 go-git 检出指定 Commit。镜像统一交给隔离的 Docker-in-Docker/BuildKit 节点构建，不允许占用发布目标主机的 CPU、磁盘和构建权限。绑定镜像仓库时，由构建节点推送镜像并使用不可变 Digest 发布；未绑定时，仅允许 Docker SSH 环境，ZRT 使用 Commit 与运行 ID 生成唯一 `zrt.local` 标签，将 Moby `ImageSave` 返回的镜像流直接送入目标主机的 `docker image load`，随后在替换容器前校验内容寻址的镜像 ID。整个传输过程不在 ZRT 容器落地完整镜像，也不挂载宿主机 Docker Socket。Kubernetes 节点仍必须使用集群可拉取的镜像仓库。只有发布记录成功后流水线才会完成；旧版只推进节点状态却没有发布记录的伪成功运行会在迁移时改为失败。任意脚本仍不会直接放进 ZRT 主进程执行，避免缺少隔离执行器、日志归档和步骤级幂等保护时造成不可控副作用。

Dockerfile 构建复用 Docker-in-Docker 持久卷中的 BuildKit 本地层缓存；绑定镜像仓库时还会维护 `zrt-cache` 标签作为跨构建节点缓存，未绑定时则只维护构建节点中的本地缓存标签。构建上下文遵守 `.dockerignore`、始终排除 `.git`，且最大为 1 GiB。缓存拉取或缓存标签更新失败只记录结构化告警，不会覆盖正式镜像构建、镜像传输、摘要校验和发布的真实结果；Redis 不保存源码包或镜像层。

失败运行可以从页面重新执行。ZRT 不修改原失败记录，而是使用原 Git Ref 和 Commit、新建运行与 NATS 任务，并通过 `retry_of_id` 保留审计链。构建方案、镜像仓库、部署方案和流水线读取重新执行时的应用当前有效配置，因此修正配置后无需删除旧记录；生产审批不会复用，必须在新运行中重新完成。

发布计划内部创建发布组。一个发布组选择多个应用并配置组内并行或串行、失败即停止或记录失败后继续；发布组之间可以建立前置依赖，服务端拒绝循环依赖。发布计划、流水线运行和发布记录在同一页面通过页内标签切换。流水线运行可以删除，删除时一并清理审核记录和仓库快照；已经形成的独立发布记录不会随之删除。发布记录是不可编辑的历史结果。

原 `deployment_targets` 数据现在作为独立“发布环境”继续使用，并通过 `/api/v1/environments` 提供兼容后的资源接口。环境名称可自定义，环境级别只承担开发、预发布和生产保护语义；新建 Docker 环境选择已经通过表单验证的 SSH 主机及容器名称，绑定镜像仓库时发布前执行受控的 `docker pull`，未绑定时接收流水线从 Docker-in-Docker 构建节点传来的 `docker save` 镜像流并执行 `docker load`。Kubernetes 环境选择集群、命名空间、Deployment 和容器。流水线的逻辑阶段与发布环境分离，部署节点必须显式选择发布环境。旧 `/api/v1/deployment-targets` 接口和已有 Docker API 连接继续兼容，现有数据无需复制或破坏性迁移。

## 错误与审计

数据库、Redis、NATS、网络地址、调用栈和原始依赖错误只进入结构化日志。HTTP 客户端只收到稳定、可展示的中文错误和请求 ID。身份、角色、仓库、集群、发布、配置、通知、监控、调度、任务与终端操作均受 RBAC 控制并写入审计记录。

## 企业登录

ZRT 保留本地账户登录，同时支持 LDAP、通用 OAuth、飞书、Google、GitHub 和 GitLab。登录方式集中在“系统设置 → 登录方式”中管理，并继续使用独立的身份读取和管理权限；客户端密钥和 LDAP 查询密码使用 `ZRT_SECRETS_KEY` 加密，接口只返回“已配置”，不会回显原文。

- LDAP 先用只读服务账号查找唯一用户，再使用该用户的 DN 和密码重新绑定；默认要求 LDAPS 或 StartTLS。明文 LDAP 只有管理员明确勾选后才允许。
- OAuth 授权请求使用一次性 state 和 PKCE，状态保存在 Redis 中并在回调时原子消费，十分钟后自动过期。回调地址来自管理员保存的配置，不信任请求的 Host 头。
- 外部身份只按“登录方式 + 外部唯一 ID”绑定。ZRT 不会因为邮箱相同自动合并本地账户，避免可伪造邮箱造成账号冒领。
- 管理员可以允许首次登录自动创建普通用户，并选择一个默认角色；未选择角色时，新用户可以登录但没有业务权限。外部登录不会创建超级管理员。
- 停用登录方式会立即阻止新的登录请求，但不会强制中断已经建立的会话；需要立即收回访问时，应同时停用对应用户。

迁移新增 `identity_providers` 和 `external_identities` 两张表，不修改已有用户、密码或角色。升级后所有外部登录方式默认不存在，本地管理员登录行为保持不变；管理员配置并启用某个登录方式后，它才会出现在登录页。
