# EDO 发布执行的项目授权边界

HTTP 上的动作授权与后台任务执行授权分别检查。独立发布、回退和命令脚本任务即使不使用变量或密钥，也不能在排队后继续沿用已经撤销的角色权限。

- 任务上下文必须已经携带冻结的项目和部门，并与发布记录一致。缺失范围时拒绝执行，不根据发布记录推测或切换范围。
- 独立发布和回退使用发布记录的 `requested_by`，从数据库实时核对账户、项目成员、角色动作及个人拒绝项。回退需要当前操作者拥有 `deployment.execute`，不依赖来源流水线过去的授权人仍有效。
- 流水线发布核对运行、应用、项目、部门和原请求人，再使用不可变运行快照中的 `authority_id` 检查 `pipeline_run.execute`。自动触发的 `system` 不是可授权账户，也不会被赋予权限；实际授权人必须存在且仍有当前项目执行权限。流水线发布不额外要求原请求人拥有手动发布权限。
- 获取执行资格之前及实际调用 Docker、Kubernetes 或命令执行器之前再次检查，避免等待锁或准备执行期间发生撤权后继续产生副作用。已有同步 HTTP 权限、变量与密钥使用权限继续独立生效。
- 有效范围内的排队或执行中任务若授权失效，发布记录标记为失败，错误码为 `deployment_authorization_revoked`。缺失或错误范围不会改写其他范围的历史。发布与回退任务仍只执行一次，不自动重试。
- 已成功发布的任务在相同项目范围内重复投递时直接确认成功，不再调用外部运行时，也不会因后续撤权把既有成功任务改成失败。

本调整不变更数据库结构，也不补写历史授权。旧排队记录若没有原请求人、准确项目和部门，或者流水线运行快照没有 `authority_id`，会明确拒绝执行；管理员应核对当前项目角色及部署配置后，从正常流水线或回退入口重新确认，不通过猜测身份、补授全局权限或直接重投旧任务恢复。
