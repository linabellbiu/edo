# EDO 统一发布模型

应用、流水线、构建与部署方案、环境、变量与密钥、运行和制品均按项目隔离。本文中的共用方案只在当前项目内复用，不跨项目共享用户配置；执行始终使用运行快照的项目范围，修改或执行时分别检查该项目有效权限。

资源列表按当前用户在所选项目的有效查看权限展示，包含其他成员创建的资源和停用草稿。流水线列表同时列出“共用方案”和“应用流水线”，显示归属、关联应用、阶段及任务数量；搜索和归属筛选均可清除。查看应用流水线只需要流水线查看权限，不额外要求应用列表权限；修改、删除和执行仍分别检查对应权限。个人凭据及密钥内容继续遵守各自所有权与独立授权规则。相关验证见[列表可见范围验收](list-visibility-acceptance.md)。

流水线运行记录的“阶段耗时”列展示本次运行中各阶段的实际用时，详情流程图在阶段标题下显示相同数据。阶段从首个任务进入执行队列开始计时，到该阶段最后一个实际任务结束为止，包含排队、审核和人工放行等待；并行任务取整体时间跨度，不累加各任务耗时。运行中持续计时，完成后固定；未开始、未执行、跳过和历史时间缺失分别显示，不用零值代替未知。实现及验收边界见[阶段耗时说明](pipeline-stage-timing.md)。

EDO 的交付关系统一为：**应用 → 流水线 → 部署方案 → 运行资源**。Docker 单容器、Docker Compose、Kubernetes Deployment 和主机脚本复用同一条应用流水线、制品校验、运行快照、权限及审计机制。

代码仓库归属应用；流水线构建任务引用构建方案，Dockerfile 构建方案按需引用镜像仓库；部署任务引用部署方案，由方案保存具体运行位置。不会增加独立的直接发布接口或新的执行器。

## 配置入口

在应用详情中点击“配置发布流程”，依次选择部署方式、流水线方案、部署方案、构建方案、环境及运行位置。未选择公共流水线方案的新应用不再由页面隐式创建空白流水线，而是引导用户完成此配置；已有 API 调用的创建行为保持兼容。

Kubernetes Deployment 的操作菜单提供“关联应用”，携带当前集群、命名空间、Deployment 和首个容器的名称进入相同配置抽屉，用户可以检查并修改。该入口只创建关联配置，不修改集群资源；当前 Kubernetes 发布仍更新已存在的 Deployment，私有镜像的拉取凭据由集群管理。

保存创建独立、未启用的应用流水线草稿及其部署配置，不会投递任务或执行发布。用户检查代码源事件和运行位置后再启用，通过现有手动执行或仓库事件启动。主机脚本的内置方案包含明确失败的示例脚本，必须替换为实际命令才允许启用。

## 默认方案

流水线方案和部署方案页面均提供“发布默认方案”入口，按**项目 + 部署方式**分别保存默认的流水线方案、部署方案。四种方式均有服务端维护的内置默认：代码源（默认仅人工启动）→ 构建制品 → 部署。选择构建方案时，Kubernetes 必须使用带镜像仓库的 Dockerfile 构建，主机脚本必须使用保存文件制品的脚本构建。

用户可选择已启用的自定义方案作为默认，或恢复“内置默认”。用于此快捷配置的公共流水线方案包含一个构建任务和一个部署任务，可以增加测试、审核和放行等其他任务；复杂的多构建、多目标流程继续使用现有完整编辑器。

默认值只是新建时的预选。创建时复制通用编排和部署规则，为当前应用生成独立部署方案及目标，不复制原方案的实际主机、集群、命名空间、工作负载、容器或目录。新工作流是独立自定义配置，后续默认值或公共方案变化不会改写它；原有明确绑定公共流水线方案的最新启用版本跟随语义保持不变。

部署方案可以保存为“通用部署方案”，仅保存运行参数，不关联实际环境。公共流水线方案可引用通用部署规则，但应用流水线必须绑定具体位置才可启用。已有固定目标方案保持可用，并且不能通过勾选通用模式移除它的目标；设为默认时也只复制规则。

默认项采用版本校验和项目行锁；并发修改返回冲突，要求刷新。默认引用失效时明确显示不可用，并拒绝按失效默认创建，不静默改用其他位置。默认设置需要流水线和部署方案的修改权限；创建流程同时检查应用、流水线、构建、部署方案和基础设施的相关权限，资源始终受当前项目范围约束。

## 多镜像 Compose 与已有部署

一条流水线分成两个阶段：**并行构建与推送镜像 → Compose 部署**。Compose 正文保存在 EDO 部署方案，部署读取本次上游实际产出的镜像 Tag，并固定为对应摘要执行 `docker compose up -d --no-build --pull never --wait`。不需要额外的清单汇总任务，也不读取目标主机原 Compose 文件作为发布配置。

页面入口为“应用 → 配置发布流程 → Compose 与 Tag（多镜像）”：

1. 填写 Compose 项目名，在 YAML 编辑器粘贴完整 Compose。需要保留原数据库和卷时，准确沿用原项目名、卷、网络、端口与服务配置；移除 `build`、`include` 和 `extends`。编辑器支持行号、高亮、格式化和行列错误定位，无效输入不会被格式化覆盖。
2. 业务服务的 `image` 写成 `registry.example.com/team/api:${EDO_IMAGE_TAG}`。设置构建镜像 Tag，例如 `${EDO_GIT_TAG}`；Compose Tag 引用默认 `${EDO_IMAGE_TAG}`。其他环境变量可在「变量与密钥」按应用、环境保存 env 文本或命名 env 文件，再在部署任务中引用；EDO 自动合并 `environment` 或添加 `env_file`，不在 YAML 写明文密码。命名文件模式需要 Compose 2.30 或更新版本。
3. 选择服务、带镜像仓库的 Dockerfile 构建方案及输出镜像名称。多个服务使用相同构建方案和镜像名时，共用一个构建任务；不同输出镜像并行构建。构建配方中的 Dockerfile、上下文、目标阶段和仓库均可独立配置。多个构建不能覆盖同一仓库、镜像名称和 Tag。
4. 选择环境、SSH 与 Docker 能力均已就绪的目标主机、绝对部署目录，可选环境文件、健康检查及免密码 sudo。接管已有项目时开启接管校验。
5. 创建草稿后，在流水线编辑器配置代码源事件、分支与 Tag 规则，再启用。创建草稿不会构建、推送或部署。

生成的任务和部署方案仍可分别编辑。Dockerfile 构建任务提供镜像名称与 Tag 字段；Compose 多镜像部署任务提供服务到上游构建的映射、项目名、Tag 变量和运行设置。Compose 正文在“部署方案”中查看及修改，运行快照固定当时配置，后续编辑不改变已开始的发布。镜像名称、Tag、仓库、分支、目录和主机都由用户配置，没有特定业务仓库的内置逻辑。

部署严格检查每个镜像的项目、应用、运行、构建节点、提交、可用状态和已登记仓库。映射服务的 image 表达式必须准确匹配实际构建的镜像名称与 Tag；共享 Tag 变量要求这些构建产物具有相同 Tag。实际执行使用不可变 `@sha256:` 引用，目标主机通过 EDO 已保存的仓库认证拉取镜像，凭据不写入脚本。其他固定依赖镜像仍由 Compose 按配置拉取，所需私有认证需在目标主机可用。

目标主机需安装 Docker Compose v2 或更新版本，并支持 `--wait`、`--no-env-resolution` 和 `--no-path-resolution`；配置健康地址时还需 curl。Compose 使用所选项目名和工作目录，按 EDO 正文更新整套配置，不在主机编译，不执行 `down` 或删除卷。接管时核对映射服务已存在、原工作目录身份一致、同服务实例没有混用旧镜像。

更新前记录旧镜像，先拉取再更新，随后逐实例核对镜像并执行可选健康检查。拉取失败不更新；更新失败尝试恢复并保留本次失败状态。首次接管只能用当前 EDO 配置恢复旧镜像，不能恢复未保存的原配置；后续发布可恢复上一次 EDO 配置。卷数据与数据库变更不由此机制回滚。原配置发生结构调整前，应先评估影响并保存必要备份。

私有执行日志及版本配置保存在部署目录 `.edo/compose/<项目名>/`，同目录同项目共用发布锁。进程强行终止可能留下锁，需要核对现场后处理，不自动清锁或无限重试。正常流水线日志显示阶段、实际镜像 Tag 和执行结果；Compose 原始输出只进入目标主机受限日志文件，避免环境变量泄露。

使用 Git 子模块时，EDO 按父提交的 gitlink 检出固定版本。同协议、主机和端口的子模块可复用主仓库认证；主仓库使用 HTTPS Token 时，私有子模块也应使用同站 HTTPS 地址。SSH 地址需要独立的 SSH 认证，不能用 HTTPS Token 代替；跨站子模块不自动获得主仓库凭据。

原“Compose 单镜像”方式继续适用于单个上游镜像的容器参数配置。脚本或 Shell 任务仍可按需读取 `EDO_UPSTREAM_ARTIFACTS_JSON`；多镜像向导不依赖此汇总方式。

## 应用内流水线名称

同一应用中尚未删除的流水线不能重名，停用草稿也参与检查。手动改成已有名称时拒绝保存，原名称、版本和任务配置保持不变；不同应用可以使用相同名称，已删除的名称可以重新使用。

默认创建和已绑定方案的版本同步沿用数字后缀分配，例如“发布”“发布 2”“发布 3”，不覆盖独立流水线。名称最多 128 个字符，添加后缀时保留完整字符及数字。最终仍按数据库的名称比较规则检查；发生冲突或写入失败时整次修改回滚，不留下只同步一部分的结果。

名称检查和修改复用现有 GORM 事务与应用行锁，不新增组件或数据库迁移。此次修复不自动合并、重命名或删除已有重复记录，不改变权限、草稿自动保存和已启动运行的快照。

## 兼容性与实现选择

迁移 `202610230067` 只新增 `delivery_defaults` 表及项目与类型联合唯一索引。未保存时使用服务端内置定义，无需向每个项目写入预置记录。不会重归属、改写或删除既有应用、流水线、部署目标、发布记录或运行快照。

业务编排和默认选择属于 EDO 自身规则，使用已有 GORM 事务及版本校验实现，无需引入新的工作流组件或常驻服务。部署继续复用项目已使用的 Docker/Moby、Compose 与 Kubernetes client-go 路径，不引入额外 SDK。运行时仍从原有执行快照固定构建、部署方案和目标；修改默认或配置不影响已经启动的运行。
