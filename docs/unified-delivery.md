# EDO 统一发布模型

应用、流水线、构建与部署方案、环境、变量与密钥、运行和制品均按项目隔离。本文中的共用方案只在当前项目内复用，不跨项目共享用户配置；执行始终使用运行快照的项目范围，修改或执行时分别检查该项目有效权限。

EDO 的交付关系统一为：**应用 → 流水线 → 部署方案 → 运行资源**。Docker 单容器、Docker Compose、Kubernetes Deployment 和主机脚本复用同一条应用流水线、制品校验、运行快照、权限及审计机制。

代码仓库归属应用；流水线构建任务引用构建方案，Dockerfile 构建方案按需引用镜像仓库；部署任务引用部署方案，由方案保存具体运行位置。不会增加独立的直接发布接口或新的执行器。

## 配置入口

在应用详情中点击“配置发布流程”，依次选择部署方式、流水线方案、部署方案、构建方案、环境及运行位置。未选择公共流水线方案的新应用不再由页面隐式创建空白流水线，而是引导用户完成此配置；已有 API 调用的创建行为保持兼容。

Kubernetes Deployment 的操作菜单提供“关联应用”，携带当前集群、命名空间、Deployment 和首个容器的名称进入相同配置抽屉，用户可以检查并修改。该入口只创建关联配置，不修改集群资源；当前 Kubernetes 发布仍更新已存在的 Deployment，私有镜像的拉取凭据由集群管理。

保存创建独立、未启用的应用流水线草稿及其部署配置，不会投递任务或执行发布。用户检查代码源事件和运行位置后再启用，通过现有手动执行或仓库事件启动。主机脚本的内置方案包含明确失败的示例脚本，必须替换为实际命令才允许启用。

## 默认方案

流水线方案和部署方案页面均提供“发布默认方案”入口，按**项目 + 部署方式**分别保存默认的流水线方案、部署方案。四种方式均有服务端维护的内置默认：代码源（默认仅人工启动）→ 构建制品 → 部署。选择构建方案时，Kubernetes 必须使用带镜像仓库的 Dockerfile 构建，主机脚本必须使用保存文件制品的脚本构建。

用户可选择已启用的自定义方案作为默认，或恢复“内置默认”。用于此快捷配置的公共流水线方案包含一个构建任务和一个部署任务，可以增加测试、审核和放行等其他任务；复杂的多构建、多目标流程继续使用现有完整编辑器。

默认值只是新建时的预选。创建时复制通用编排和部署规则，为当前应用生成独立部署方案及目标，不复制原方案的实际主机、集群、命名空间、工作负载、容器或目录。新工作流是独立自定义配置，后续默认值或公共方案变化不会改写它；原有明确绑定公共流水线方案的最新启用版本跟随语义保持不变。

部署方案可以保存为“通用部署方案”，仅保存运行参数，不关联实际环境。公共流水线方案可引用通用部署规则，但应用流水线必须绑定具体位置才可启用。已有固定目标方案保持可用，并且不能通过勾选通用模式移除它的目标；设为默认时也只复制规则。

默认项采用版本校验和项目行锁；并发修改返回冲突，要求刷新。默认引用失效时明确显示不可用，并拒绝按失效默认创建，不静默改用其他位置。默认设置需要流水线和部署方案的修改权限；创建流程同时检查应用、流水线、构建、部署方案和基础设施的相关权限，资源始终受当前项目范围约束。

## 多镜像 Compose 与已有部署

Compose 本身支持多个镜像。EDO 的内置 Compose 方案在一次部署任务中固定一个上游镜像，其他依赖服务可以使用固定镜像；其内联 YAML 不读取宿主机的 `env_file`，也不自动接管已有项目的数据卷。

已有多镜像栈可以使用主机脚本方案：前序阶段分别用 Dockerfile 构建任务构建、推送镜像，随后用脚本构建任务生成发布清单文件制品，最后由主机脚本消费清单并执行 `docker compose up -d --no-build`。部署阶段不重新检出或构建源码。接管前核对原项目名、工作目录、配置、网络与持久卷；保留回退版本，不能用新空卷替代旧数据。

页面入口为“应用 → 配置发布流程 → 已有 Compose 项目（多镜像）”。填写目标主机已有项目的准确名称、Compose 文件、可选环境文件和绝对部署目录，为每个服务选择带镜像仓库的 Dockerfile 构建方案。同一构建方案供多个服务使用时只构建一次；不同 Dockerfile、上下文、目标阶段和仓库沿用各自构建方案。主机需要 SSH、Docker 就绪并属于所选环境，页面选择必须与环境实际解析的主机一致。

此向导是通用模板，不包含某个仓库、分支、镜像名称或服务器地址。它原子创建独立的三个阶段草稿：构建与推送 → 汇总摘要 → Compose 更新；继续使用普通构建方案、主机脚本、流水线快照、权限与审计。创建额外检查 `build_plan.create` 权限，失败整体回滚，不自动启用或触发发布。生成后可在流水线及构建、部署方案页面查看和修改；代码源事件及 Tag 规则仍在流水线编辑器配置。

汇总任务使用页面指定的、按需启动的 Node.js 镜像，不要求目标主机安装 Node.js 或 Python。目标主机只需 Docker Compose 和原有配置；配置健康地址时还需要 curl。镜像推送使用构建方案的仓库凭据，目标主机必须已有拉取这些镜像的权限；向导不导出仓库密码到脚本。

已有项目模板会只读校验配置、项目服务与原工作目录，记录旧 Image ID，先拉取本次 Digest，再执行带 `--no-build --no-deps --wait` 的 `up -d`，随后逐实例核对镜像并执行可选健康检查。不会运行 `down`、删除卷、重建依赖或在主机构建。选中服务在原项目中不存在、同一服务已有混合版本或目录不符时停止接管。失败尝试恢复旧镜像且仍记录本次失败；恢复也失败时明确保留现场。每次私有执行日志、镜像清单与旧镜像保存在部署目录 `.edo/compose/<项目名>/`；同目录、同项目的不同流水线共用发布锁。进程被强行中断可能留下锁，须核对现场后由管理员处理，不自动清理或重跑。

此模式保留目标主机原有 Compose 与环境文件，只替换映射服务的镜像和版本标签。仓库里的 Compose 结构变化不会被静默覆盖到现有主机；新增服务、数据库升级或更改卷、网络时应单独审核原配置。新项目仍可使用内置 Compose 方案。

脚本构建和 Shell 任务可读取保留变量 `EDO_UPSTREAM_ARTIFACTS_JSON`。它是前序阶段中本次运行已成功构建的制品数组，每项包含 `node_id`、`id`、`kind`、`storage_kind`、`digest`、`image_ref` 和 `commit_sha`。不包含同阶段任务、其他运行、失效制品、凭据或存储路径；清单最大 64 KiB。多镜像发布清单应逐项检查所需节点、固定提交与 `@sha256:` 镜像引用，缺少任何镜像均停止发布。

Dockerfile 构建参数支持替换 `${EDO_COMMIT_SHA}`、`${EDO_GIT_REF}`、`${EDO_PIPELINE_RUN_ID}`、`${EDO_APPLICATION_ID}`。例如 `TE_SOURCE_REVISION=${EDO_COMMIT_SHA}` 会在本次运行中固定为完整提交。此替换不执行 Shell，也不展开任意宿主机环境变量；敏感值继续使用 BuildKit Secret，不放入构建参数。

仓库检出会按父提交的 gitlink 获取子模块固定版本，不跟随子模块分支。沿用 go-git 的配置解析与传输，跨远端身份不转发父仓库凭据；跨站私有子模块目前会明确失败，不会借用其他仓库凭据。仅允许仓库已有的安全传输规则，不接受本地文件地址或符号链接路径；最多 4 层、64 个子模块，受检出总超时限制。Git 配置与凭据不进入构建工作区。

## 应用内流水线名称

同一应用中尚未删除的流水线不能重名，停用草稿也参与检查。手动改成已有名称时拒绝保存，原名称、版本和任务配置保持不变；不同应用可以使用相同名称，已删除的名称可以重新使用。

默认创建和已绑定方案的版本同步沿用数字后缀分配，例如“发布”“发布 2”“发布 3”，不覆盖独立流水线。名称最多 128 个字符，添加后缀时保留完整字符及数字。最终仍按数据库的名称比较规则检查；发生冲突或写入失败时整次修改回滚，不留下只同步一部分的结果。

名称检查和修改复用现有 GORM 事务与应用行锁，不新增组件或数据库迁移。此次修复不自动合并、重命名或删除已有重复记录，不改变权限、草稿自动保存和已启动运行的快照。

## 兼容性与实现选择

迁移 `202610230067` 只新增 `delivery_defaults` 表及项目与类型联合唯一索引。未保存时使用服务端内置定义，无需向每个项目写入预置记录。不会重归属、改写或删除既有应用、流水线、部署目标、发布记录或运行快照。

业务编排和默认选择属于 EDO 自身规则，使用已有 GORM 事务及版本校验实现，无需引入新的工作流组件或常驻服务。部署继续复用项目已使用的 Docker/Moby、Compose 与 Kubernetes client-go 路径，不引入额外 SDK。运行时仍从原有执行快照固定构建、部署方案和目标；修改默认或配置不影响已经启动的运行。
