# EDO 敏感与危险操作 RBAC 审计

审计日期：2026-10-29。源码基线：`main d70c4ea`。本轮检查接口、业务服务、后台任务、权限目录及长连接，重点核对密钥读取、授权委派、命令执行、发布控制、清理和撤权。

本报告区分三类问题：已复现的授权边界缺口、已有鉴权但无法独立分配的敏感动作、需要明确的执行策略。不能把它们统称为“接口没有 RBAC”。本轮没有复现匿名用户直接执行危险操作。下文问题描述保留审计基线行为，后续已经落地的修复单独记录，不把已修项继续算作待修。

## 范围与证据边界

- 审计复现使用独立 SQLite、合成用户和密钥、假运行时、假传输或本机 `httptest` 接收器；附加审计测试通过 Go overlay 加载。确认问题后修改本次业务源码并增加持久回归，真实查询另外使用独立 MySQL，不修改业务数据库。
- 没有读取真实凭据、连接生产参考站或现有 Kubernetes 配置，没有执行真实 Shell、SQL、Docker 删除、SSH 安装或 DNS 记录变更。
- 本报告是源码与隔离复现结果，不代表当前运行实例或远程部署已经修复。本轮不重复正常 Docker 发布与岗位验收，也不以此前验收通过证明本轮边界安全。
- 另一会话正在开发 K3s 卸载，相关未提交文件已保留。基线没有独立安装权限；正在开发的卸载权限不算已发布能力，也不能据此判定卸载完全无鉴权。
- 私有证据中的 PASS 可能表示风险成功复现；安全断言的 FAIL 表示发现缺口。两者均不表示修复回归通过。

## 优先修复：已复现的权限边界缺口

### 1. P1：登录方式默认角色绕过权限委派上限

现有权限为 `identity.create` / `identity.update`。`internal/identity/service.go:247` 仅检查默认角色存在，没有验证操作者能否委派该角色的全部权限；更新接口的业务方法没有接收操作者。首次绑定身份时，`:369` 直接写入该默认角色。

隔离 HTTP 测试中，只有登录方式创建权限、没有 `user.create`、`user.update`、`role.update` 的用户，创建用户接口返回 403，却能以 201 配置包含更高平台权限的默认角色。服务测试进一步确认首次登录身份实际取得该角色。这里未赋予超级管理员标志，但已绕过普通角色授权的子集校验。

修复要求：创建和修改均传入真实操作者，在事务内复用当前数据库权限的委派校验；默认角色选择与后端使用相同范围。自动开户与角色分配应作为独立危险动作，例如 `identity.provision.assign`，而非只依赖普通登录方式编辑。

### 2. P1：修改仓库地址可将他人的个人凭据带到新目的地

现有权限为 `repository.update`。`internal/repository/service.go:833` 无条件继承原 `CredentialID` 和隐藏凭据；只有显式提交新的 `credential_id` 时，`:846` 才执行个人所有者检查。

复现：用户 A 以个人令牌绑定原仓库，用户 B 修改连接地址并省略凭据字段；保存成功。假 Git 传输收到“新地址 + A 的原令牌”。未向真实外部地址发请求。显式测试连接需要 `repository.execute`，但正常后台轮询和仓库引用读取同样会使用保存的凭据，因此仅限制测试按钮不解决问题。

修复要求：凭据授权绑定目的地身份；更换目的地不能继承他人隐藏凭据，必须重新提供凭据或选择当前用户拥有的引用。同一目的地修改名称、分支可以继续保留原引用。单独增加凭据修改权限不能替代个人所有权边界。

### 3. P1：运行控制或删除等待锁后没有重新检查撤权

接口已经检查 `deployment.execute`，但 `internal/deployment/control.go:191`、`:242` 等待目标锁后，仅重新读取当前部署记录，随后在 `:213` 执行控制，或在 `:269` 删除 Docker 运行实例。

隔离 SQLite、Redis 锁与假 Docker 测试分别验证：等待期间撤销角色动作、增加个人拒绝、移除项目成员、停用用户、停用项目，释放锁后仍调用控制或删除。删除测试只收到本机假服务的 DELETE，没有删除真实容器。

修复要求：获得锁后、真正副作用前，按当前数据库和冻结的操作者重新验证项目、成员、用户及动作权限。对外应返回稳定的中文权限提示和 403，不能把新增授权错误映射为 500。不要用入口检查替代等待后的检查。

### 4. P1：检出代码期间撤权，之后仍新启动脚本

`internal/pipeline/build_executor.go:78` 在任务开始检查流水线执行权限；检出完成后直接进入节点执行。`:608` 的脚本路径仅在有变量绑定时另查变量使用权限，没有再次检查主要的 `pipeline_run.execute`。

隔离测试在检出阶段撤销执行权限，并确认当前数据库有效权限已经拒绝，脚本运行器仍被新调用一次。运行器为 Stub，未执行真实命令。这不是要求撤回已经发生的副作用，而是阻止撤权后开始新的副作用。

修复要求：检出、锁等待、镜像准备等阻塞准备结束后，在 Shell、Docker 构建和部署前重新鉴权；明确长任务的撤权取消策略。

### 5. P1：K3s 后台授权依赖可能过期的 Casbin 策略

基线 `internal/k3s/service.go:92` 的安装与加入授权检查当前用户、成员和项目，但对动作仅调用缓存策略 `HasPermission`，未同时使用当前数据库有效权限。后台轮询复用该检查。

独立 SQLite 加真实 Casbin 的测试先加载允许策略，再在数据库撤销角色动作或增加个人拒绝：`FreshProjectPermissions` 已拒绝、缓存仍允许，安装/加入授权继续成功。覆盖 `cluster.create`、`cluster.update`、`cluster.execute`、`kubernetes.node.create` 共八种组合；远程写入次数为零。

这证明缓存未同步时的防线缺失，不证明所有正常撤权接口必然留下旧策略。HTTP 通用项目权限中间件已有缓存与当前数据库双检查，后台同样应采用。

状态：负责 K3s 的会话已在 `3bb6cec` 提交双检查与持久回归，提供完整包及后续增量定向竞争检测通过的证据；固定最终 Commit 的完整验收与激活仍由该会话负责。这里不称远程安装或部署已验收。

### 6. P1：项目停用和删除也缺少当前动作权限复核

`internal/access/projects.go:127` 的 UpdateProject 与 `:306` 的 DeleteProject 先验证当前项目成员，再仅调用缓存 `HasPermission`。项目路由未额外经过通用动作权限中间件，因此缓存未同步时，没有数据库动作权限的第二道防线。

独立 SQLite 与真实 Casbin 共十二个用例：直接在隔离数据库撤销角色动作或增加个人拒绝后，当前权限已拒绝，缓存仍允许，停用项目和删除空项目成功，四个安全断言失败；使用正常授权服务更新角色或个人权限，会同步缓存并正确拒绝，四个对照通过；移除成员的两个对照正确拒绝，两个有效授权对照正常成功。删除仅发生在隔离测试库的新建空项目。

修复要求：两个业务方法修改前补当前数据库有效动作校验，删除时在事务内复核，复用现有的权限拒绝与 403 映射。这仍是缓存同步延迟条件的防护缺口，不能宣称正常撤权接口必然失效。另一会话已在 `359bc71` 提交修复，提供十九个项目管理场景及相关竞争检测通过的证据；合法管理者仍能重新启用停用项目，普通业务访问继续拒绝。

## 缺少独立权限的敏感与危险动作

以下动作当前均有 RBAC；问题是岗位无法按最小职责单独分配。新权限码是设计建议，尚未实现或生效。

| 动作 | 当前权限 | 建议分配粒度 |
| --- | --- | --- |
| 用户资料、停用、角色与显式权限分配 | `user.update` 共用 | 普通资料与授权管理分开；委派上限仍必须检查 |
| 角色名称与授权内容修改 | `role.update` 共用 | 角色资料与角色授权分开 |
| 登录方式信任配置、自动开户、默认角色 | `identity.create/update` 共用 | 认证配置与自动授权分开，均明确高风险 |
| K3s 安装 | `cluster.create/update/execute` 等组合；execute 文案仅描述测试连接 | 独立 `kubernetes.k3s.install`，区分测试连接、接入和主机软件安装 |
| 已发布 Docker 运行实例的重启、停止、缩扩容、回滚、删除 | `deployment.execute` 共用 | 至少把 `runtime.remove`、停止、回滚与普通运行/重启分开 |
| 流水线启动、停止、重试、人工推进 | `pipeline_run.execute` 共用 | 对停止、重试、人工推进分别授权；审批保留独立 review |
| 制品元数据与文件下载 | `artifact.read` 共用 | 独立 `artifact.download` 并记录下载审计；当前下载路由未配置操作审计 |
| 定时通知创建与直接启用 | `scheduler.create/update`；创建即 active | 普通编辑可保存草稿；启用和立即产生发送行为用独立 `scheduler.execute` / `notification.send` |
| 登录锁定、安全设置、助手地址与其他系统配置 | 平台 `config.update` 共用 | 安全设置、认证信任、密钥目的地等分别分配高风险权限 |
| 日志、缓存、工作区和本地产物清理 | 平台 `config.execute` 共用 | 审计保留/清理、本地产物删除与普通缓存维护分开，保留范围预览、确认与审计 |
| 发布保护的关闭、人数降低、审核人替换 | `environment_policy.update` 共用 | 明确标高风险；按需要拆保护策略变更权限，运行时继续绑定版本 |

定时任务的权限粒度已用隔离 HTTP 复现：只有 `project.read + scheduler.create` 的用户，通知测试为 403，却能创建立即活跃的通知任务。当前 `notification.execute` 的定义明确仅为“发送通知渠道测试消息”，所以不能直接要求所有业务通知复用这个权限，应该明确新增业务发送/启用语义。

监控规则创建、启用和真实探针也应复核相同粒度，但本轮仅完成源码检查，没有将其列为已动态复现的越权。

登录方式的上游信任修改尤其不能按普通资料编辑授予：新 provider 不会按邮箱或同名合并旧用户，但已有 `(provider_id, subject)` 的绑定会继续登录原账户。允许修改原 provider 的上游和声明映射，本身就拥有影响这些账户认证的能力；默认角色子集校验只解决新用户授权，不能把认证信任管理降为低风险。目录本次已明确提示该影响，后续宜拆分信任修改与显示名称等普通资料。

## 目录中的危险标识不准确

审计基线中，`internal/access/permissions.go` 的 `user.update`、`role.update`、`identity.create/update`、`config.update` 为 `Dangerous=false`。`internal/access/project_permissions.go` 将构建/流水线/部署方案编辑以及环境保护修改也标为非危险，实际可以影响脚本、目标和审批要求。本次已修正这些标识，权限拆分仍按上表单独跟踪。

应依据真实能力显示风险，权限分配页面清楚展示作用范围和影响。`Dangerous` 是目录与 UI 元数据，改为 true 不会自动补上后端授权，也不能替代独立动作与委派校验。

## 后台任务还需明确的策略

### 已复现：停用定时任务不阻止已排队载荷

`internal/scheduler/service.go:158` 的 Execute 只检查载荷格式，没有重新读取任务启用状态或版本。隔离测试“排队 → 停用 → Execute”仍创建一条通知记录，没有实际派发。

建议把停用的语义定义为不再产生后续副作用，执行时重验任务 UUID、项目/部门、启用状态与版本；过期载荷明确跳过。这同时是任务生命周期问题，不能仅通过增加入口权限修复。

### 待定策略：审核人撤权后旧票是否继续有效

流水线人数统计只计已有审核记录，执行前检查保护配置版本，没有像 SQL 工单一样复核审核人的当前权限。隔离测试中 A 合法投票后被停用，B 再合法投票，A 的旧票仍使流水线满足人数并创建下游作业。

这不是无审核权限者直接调用审批成功，而是历史签票有效期策略。建议与 SQL 统一：真正执行前复核审核人当前有效权限；若产品选择保留有效历史票，也应明确说明、记录签票时授权与撤销规则。

### 源码风险：通知派发缺少明确的执行主体

通知记录保存 Source/SourceID，没有专用授权主体与所需动作；`internal/notification/service.go:261` 的派发主要检查渠道活跃状态，然后解密发送。定时任务载荷不保存发起人，后台仅恢复项目/部门。

因此请求人撤权、项目停用后的待发通知和任务重试缺少统一的业务权限复核。应明确采用“当前用户委派”还是“项目服务身份”，保存不可变的授权依据并在派发前验证。此项只有源码证据，本轮未实际发送外部消息，不称为已复现的数据外泄。

## 已检查存在的保护

- 通用 HTTP 项目动作使用 Casbin 与当前数据库有效权限双检查；不能仅凭某条路由未直接写中间件就认定无权限，服务层也有校验。
- 正常用户/角色/项目成员授权有委派子集限制和数据库事务校验，问题集中在默认角色等旁路。
- Secret 变量不返回原文，旧 Secret 不能降为普通变量泄露；镜像仓库凭据、身份配置密文和助手 Key 在普通查询中隐藏。
- `repository.secret.read`、`kubernetes.secret.read` 已有独立敏感读取权限和审计；Kubernetes RBAC 映射修改也已有独立危险权限。
- 主机终端、容器终端及文件读取、上传、编辑有独立动作与持续授权检查，没有发现仅凭普通查看就取得任意终端的入口。
- SQL 工单区分查看、检查、审核、执行、跳过；执行还检查数据库执行权限、审核人、版本摘要、幂等与等锁后授权。
- 助手确认和实际工具执行重新检查权限，工具白名单不提供任意 Shell、SQL、删除或读取密钥原文。
- 状态及流水线日志 WebSocket 在连接、消息或输出阶段持续检查权限；未将长连接一概列为缺失撤权。
- Docker 运行实例操作绑定部署身份，没有发现可操作任意 Docker 容器的停止/删除路由。Kubernetes 写入的对象身份、动作权限和确认不能由新增独立权限替代。

## 修复与验收顺序

1. 先封堵默认角色委派、个人仓库凭据目的地、运行控制等锁后授权、检出后授权，以及 K3s 和项目管理的当前权限检查。
2. 再拆令牌原文、运行实例删除、安装、敏感配置与清理等权限；同步后端、权限目录、角色界面、菜单按钮与审计，新增权限默认不因已有宽权限而自动授予。
3. 明确定时任务停用、历史审核票及通知服务身份策略，并将执行前检查写入统一回归。
4. 用真实角色验证“允许、缺少动作、其他项目、个人拒绝、撤销成员、停用用户/项目”，再覆盖等待锁、排队、检出、重试和持续连接期间撤权；记录实际副作用次数，避免只断言 HTTP 状态。
