# EDO DevOps RBAC 真实验收计划

## 目标与范围

在另一会话已经启动的独立本地 EDO（`http://127.0.0.1:18180`）中，创建可区分职责的角色、普通用户、项目成员关系和专属业务资源，按真实工作流程验证有效权限。管理员只负责搭建和取证，不能用管理员操作成功代替普通角色验收。

主验收使用正常的 Go 后端与前端项目，分别构建 Docker 镜像并部署，通过同一条流水线模拟配置、申请、双人审批、升级、失败处理与运维回滚。实际访问前端及代理后的后端，核对角色对应的 UI 和直接接口；不要求 K3s，不以固定输出脚本替代这个项目。

本轮只测试和修复 RBAC，不重建、重启共享测试环境，不接管另一会话的 NAS/K3s 安装，不修改现有业务资源或已有用户的授权，不操作远程 EDO、CI、Runner、FRP 或本机既有 Kubernetes 连接。

创建数据统一使用本轮 `rbac-<run-id>` 标记。记录实例、源码提交、容器镜像和开始时间；环境升级后重新确认基线。测试账号凭据随机生成，仅存入本轮权限受限的临时目录，不进入代码、报告、日志或截图。

## 角色与权限模型

从实际 `/permissions` 目录解析有效动作，逐项列举权限；不使用通配符，也不把名称中带“开发”或“管理员”的已有角色当作预期权限。

| 角色 | 正常工作 | 重点拒绝 |
| --- | --- | --- |
| 验收恢复管理员 | 初始化专属测试用户、角色、部门、项目及故障恢复 | 不用于证明普通角色能够完成工作 |
| 平台组织管理员（非超级管理员） | 公司、部门、用户、角色及平台配置管理 | 未加入项目的应用、仓库、流水线、变量、发布；不能以平台角色授予项目动作 |
| 项目管理员 | 当前项目配置、成员委派及项目业务配置 | 平台管理、跨部门加人、自改角色提权、委派超过自身的权限 |
| 开发工程师 | 应用和仓库配置、查看流水线/构建、发起允许的测试运行、查看变量元数据 | 审批、环境保护修改、原文密钥、主机终端及未经批准的生产操作 |
| 测试工程师 | 查看应用、运行、制品和部署结果；发起受保护规则约束的验收运行 | 修改配置、审批、修改变量或绕过发布保护 |
| 构建维护人员 | 维护流水线、构建方案和镜像仓库连接，查看构建及制品 | 发布审批、发布保护修改、数据库执行、主机终端 |
| 发布申请人员 | 查看配置、维护专属发布计划、申请发布并查看进度 | 审批、自行修改发布保护、原文密钥 |
| 发布审批人员 | 查看申请和必要上下文，以 `deployment.review` 审批 | 发起/执行发布、修改流水线/保护规则、自审及代替其他必需审批人 |
| 项目运维人员 | 查看主机/集群/部署、执行明确授权的运行与回滚操作 | 平台管理、默认原文密钥权限；主机终端需单独授权 |
| DBA 审核人员 | 查看、检查、审核 SQL 工单 | 自审、修改他人工单、执行 SQL、自动获得跳过检查权限 |
| DBA 执行人员 | 按工单及数据库两层授权执行已审核变更 | 审核、修改 SQL、修改保护策略 |
| SQL 申请人员 | 新建、修改本人草稿并发起检查，查看本项目工单 | 审核、执行、跳过检查及修改发布保护 |
| 变量管理员 | 管理本项目普通变量和加密密钥配置 | 自动获得变量执行权限、跨项目配置和密钥原文 |
| 密钥使用人员 | 在明确引用且获准的流水线中使用配置 | 修改密钥、从页面或日志取得原文 |
| 项目只读审计人员 | 查看当前项目配置元数据、运行记录、制品和 SQL 工单 | 写入、执行、审批、终端、密钥原文、平台系统审计 |
| 平台安全审计人员 | 独立授予 `audit.read`，按需授予 `monitor.read` | 业务写入、密钥、终端；不能自动获得项目数据 |
| 未入项目、已停用及已撤权用户 | 无项目业务操作 | 列表、已知 UUID、直接地址、HTTP、WebSocket 和后台执行均不能越权 |

个人 Git 凭据继续核对所有者，不能因项目角色共享其他人的令牌。必要的个人凭据权限与项目职责分别配置。一个用户在同一项目目前仅支持一个角色，多岗位使用明确的合并角色进行测试，不暗中增加平台权限。

## 测试数据与身份安排

- 部门 D1 创建项目 A（主验证）和项目 B（同部门隔离），部门 D2 创建项目 C（跨部门隔离）。
- 为每个职责创建普通账号与独立会话；另建同一人在 A 为开发、B 为只读的交叉身份，以及平台管理员但没有项目成员身份的账号。
- 各项目创建同名应用、仓库标识、变量与密钥、流水线、构建/部署/发布方案，分别写入可识别且非敏感的哨兵值。
- 只在本轮专属资源中执行创建、修改、删除、运行和回滚；使用现有独立 Docker 构建运行时，不停止或修改其他会话资源。
- Kubernetes、远程主机和 SQL 的真实执行需有单独明确的测试目标和资源。尚未具备时记录“前置条件未满足”，不能用 404、Mock 或接口鉴权通过冒充实际执行成功。

## 按顺序执行的场景

| 阶段 | 操作与断言 |
| --- | --- |
| 1. 基线及建模 | 只读确认本地实例健康、权限目录和当前内置角色；经正常管理入口创建本轮角色、用户、部门、项目和成员。将实际创建 UUID 和权限清单写入私有清单，确认没有额外动作。 |
| 2. 正向工作 | 每个普通身份登录后选择项目，完成其日常工作。核对菜单、按钮、表单、接口返回及保存后的资源归属；只读角色实际可读，配置/申请/审批/执行各自完成对应动作。 |
| 3. 最小权限负向 | 对每个角色验证相邻权限不可替代：read/create/update/delete/execute/review，变量查看与使用，数据库查看与执行，容器与主机终端，文件查看/上传/编辑。接口须给出预期拒绝；核对拒绝前后的资源状态、运行记录和外部副作用。 |
| 4. 项目隔离与委派 | A 开发/B 只读、D2 非成员；替换项目头、查询参数、UUID 和关联资源引用；项目管理员给成员分配允许的较小角色成功，越权角色、自改角色、跨部门成员和平台权限均拒绝。 |
| 5. 完整交付 | 开发准备配置→测试查看结果→申请人员发起受保护发布→两名独立审批人审批→授权执行→失败处理→授权回滚。自审、重复审批、人数不足、非指定审批人、只有审批而无执行权限、审批人撤权均单独验证。 |
| 6. 即时撤权 | 保留已登录页面、打开的确认框、未保存编辑和已建立 WebSocket；分别减角色权限、移出项目、停用账号、换部门、停用项目和添加个人 deny。验证后续请求、待确认操作、自动保存和持续流不能继续使用旧授权。 |
| 7. 排队与历史 | 任务排队后撤销实际授权人的权限，确认在外部副作用之前停止；自动运行检查冻结授权人；回滚按当前操作者授权；成功记录重投、迟到失败和并发完成不改写成功历史。 |
| 8. 数据与凭据 | 密钥只在允许的任务中注入，不在列表/详情/错误/日志/审计中回显；跨项目同名配置不会串用；个人凭据只对所有者生效；角色模板修改及个人例外的实际作用范围必须在结果中明确。 |
| 9. 修复回归 | 对确认的缺陷先记录真实请求或页面证据，补有意义的红绿回归测试，修复后重跑原场景及相关跨项目/撤权场景。源代码回归和实际运行版本复测分别记录。 |

## 优先核实的能力边界

- 内置开发角色目前按广泛 create/update 集合授予权限，须核实环境保护、部署目标和集群修改是否超出开发职责，不能直接当作最小开发模板。
- 若收敛固定 UUID 的内置开发模板，初始化或新建项目时只对齐该模板权限，保留 UUID、成员关系及所有自定义角色。需明确记录旧模板的权限被收敛，额外运维、保护配置、审批及密钥管理由独立职责角色显式授予。
- `pipeline_run.execute` 目前未按环境独立拆分；通过真实发布保护验证开发和测试不能绕过生产审批。若做不到，作为授权功能缺口处理。
- 环境保护的审批人候选及保存校验应排除没有实际审批权限的成员；撤权后应明确阻断，而不是让运行永久等待无资格审批人。
- 项目角色模板可被多个项目共用，个人 allow/deny 当前按用户保存。核实界面呈现、可委派范围和跨项目影响；不能把全局例外误称项目定向授权。
- HTTP、后台流水线/发布、SQL 后台任务、WebSocket 和终端文件传输分别验证撤权。现有单元测试通过不能替代这些真实场景。

## 证据与交付标准

- 每个断言记录身份、项目、动作、目标、预期、实际状态码/安全错误码、关键结果和时间；不落密码、Cookie、Token、密钥值或终端内容。
- UI 缺陷保存可复现的前后截图和操作录像；权限缺陷保留脱敏请求及拒绝前后状态。发现后立即记录，修复后补对应复测证据。
- 结果使用“通过 / 失败 / 前置未满足 / 未执行”四种状态，区分静态审计、自动化代码测试、真实 HTTP、真实浏览器和真实外部执行。
- 完成时交付角色与权限矩阵、实际创建的测试资源清单、场景结果、缺陷及修复清单、剩余限制。保留专属测试数据供复核；清理仅针对本轮明确标记资源，不能删除既有业务数据。
- 本轮修复直接在 main，保留其他会话未提交改动，只提交本轮文件；不自行部署远程服务器。
