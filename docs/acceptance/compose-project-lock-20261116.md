# Compose 项目文件锁修复

日期：2026-11-16。

原脚本以 `mkdir active.lock` 加 EXIT trap 实现互斥。进程被中断时目录可能留下，后续仅凭目录存在就认定正在发布；mkdir 的权限等失败也被误报为发布锁占用。已通过内网穿透对照历史任务确认：11 月 13 日先启动的任务创建了空锁目录，另一个 SSH 地址上的并行任务撞锁，旧调度随后取消前一任务，目录一直保留。两条主机记录保存相同 SSH 指纹，使用相同工作目录和 Compose 项目。

## 实现与边界

- 发布脚本及容器重建共用 `composeconfig.ProjectLockScript`，在准确工作目录的 `.edo/compose/{实际项目}/active.lock` 普通文件上使用标准 flock；同一机器经不同 SSH 地址访问仍操作同一 inode，不依赖业务名称或地址白名单。
- 普通文件持续保留，不通过删除文件或 EXIT trap 解锁。锁随最后一个持有文件描述符的进程退出释放，子进程仍执行时继续保护实际操作。文件存在不等于锁被持有。
- 同项目发布遇忙时先记录真实等待，再按已配置执行时限内的预算等待；不同项目不互锁。容器重建保留原立即返回忙状态的交互，仍核验确认摘要和原容器、镜像及配置身份。
- 缺少工具、非普通文件、工具/文件系统异常及等待超时分别处理；重建接口返回稳定中文与 `compose_lock_unavailable`，原始诊断只进日志。不自动安装软件、不清理未知旧目录、不修改历史运行，也不通过取消并发保护来修复残留。

## 方案调研

采用 [util-linux 官方 flock](https://github.com/util-linux/util-linux/blob/master/sys-utils/flock.1.adoc) 的文件描述符形式、明确冲突退出码与有界等待。该工具持续维护、常见 Linux 发行版长期提供，作为外部命令调用，不引入或静态链接新的 Go 依赖；维护/安全更新由主机发行版承担。服务端已有 Redis 锁继续保留，但仅靠记录 ID 无法覆盖同一机器的不同 SSH 地址，因此不能替代主机上的项目锁。自行维护 PID、时间戳或目录租约易受进程复用与崩溃影响，本次不采用。主机实际检测到 util-linux 2.39.3，本地 API 镜像为 2.38.1；均已验证支持所用选项。缺少工具时明确失败，可替换性保留在共用脚本生成函数中。

## 验证

- 真实 Linux flock 验证同项目互斥、有界等待/超时、正常退出复用、强制终止后释放、inode 保持、不同项目并行、旧目录和符号链接阻断、缺少工具及异常工具分类，通过。
- 将实际流水线测试程序交叉编译后放入现有 Linux 镜像，在无网络、无 Docker socket、仅只读测试程序挂载的有限额容器中执行完整生成脚本：发布成功、拉取失败、启动失败、回滚、健康失败和日志脱敏用例全部通过。Docker 操作为桩，文件锁为真实 util-linux 工具，不作为实际业务发布验收。
- Compose 配置、流水线、部署、SSH 执行模块完整回归通过，分别为 0.012、26.305、18.189、1.248 秒；运行控制接口相关回归及重建脚本、稳定错误与日志上下文专项通过。
- 开发机没有 flock 时，原日志/回滚测试通过 Python fcntl 标准库取得实际非竞争内核锁；完整协议由上述真实 Linux 测试覆盖，没有跳过或降低原业务断言。

本次不自动重跑用户业务流水线，失败记录保持原样；实际现场处理与本地更新回执单独记录。
