# 集群连接状态卡在“检测中”的定位与修复

日期：2026-11-17

## 现象

集群列表里“测试”集群（`https://192.168.3.234:6443`，kubeconfig 接入，v1.37.1+k3s1）名称旁一直显示检测中的转圈，即使该集群实际可连接；“测试连接”能返回版本号。

## 现场证据

- 从 EDO API 容器内直接请求集群：`GET https://192.168.3.234:6443/version` 无凭据返回 401（约 50ms）；用该集群已保存的 kubeconfig（客户端证书）请求返回 200（约 20ms）。
- 用 EDO 自身的连接检查代码（同一 `connectionStatusCache` 路径、同一份 kubeconfig）在 API 容器网络命名空间中循环读取状态：2ms 内返回“已连接”，之后正常命中 30 秒缓存。
- API 日志显示：页面从 12:18:23（登录后）开始以 2.0 秒间隔持续请求 `GET /api/v1/kubernetes/clusters/connection-statuses`，40 分钟内无一次退避；响应体大小稳定对应“超时 + 已连接 + 检测中 + 已停用”，即始终有一个集群停留在“检测中”。
- 该集群在 12:18:38 曾有一次 `context canceled` 的检查记录，之后不再出现任何该集群的检查结论（成功或失败都不记录），说明这次检查的结果没有回写到状态缓存。
- 容器内 `/proc/net/tcp` 没有指向这些集群的残留连接，容器内所有线程都在 futex/epoll 等待，没有阻塞在 connect/recvfrom 上；即卡住的检查没有继续占用网络连接。

## 根因

1. 连接状态缓存按“集群 + 操作者授权”缓存一次后台检查；检查在 goroutine 中执行，结果会回写缓存。
2. 该次检查未按预期回写结果（检查卡住或结果被丢弃），缓存条目保持 `checking`，之后每次读取都直接返回“检测中”，不会再发起检查。
3. 前端只根据 `status === 'checking'` 决定 2 秒轮询，没有上限；因此“检测中”可以永久持续，页面一直转圈，手动刷新也不会清除进行中的条目。

## 修复

后端（`internal/kube/connection_status.go`）：

- 检查条目记录开始时间、序列号和名额租约。
- 读取时若发现检查超过 `检查超时 + 2 秒` 仍未回写，判定为卡住：取消该检查、回收并发名额、作废旧结果（序列号递增），并立即重新检查；本次返回明确的“连接检测超时，请重试”，重试期间保持该结论，不再显示检测中。
- 检查名额改为可重复释放的租约（`connectionCheckGate`），卡住的检查被回收后，它迟到的返回不会重复扣减名额，也不会覆盖重试结果。
- 名额占满时仍立即返回“等待检查连接”，不建立无界队列。

前端（`web/src/utils/clusterConnection.ts`）：

- “检测中”最多持续 8 秒（后台 5 秒超时 + 调度余量），超过后按“检测超时”展示，提示“连接检测超时，请重试”，状态点为中性色而不是一直旋转。
- 出现检测超时后轮询降为 10 秒，仍可自动恢复；手动刷新是显式重检，会清除上限结论并重新显示检测中。
- 集群选择器的反馈行同样显示检测超时并提供重试，不把未知状态说成已连接。

## 验证

- `go test ./internal/kube`：连接状态、并发名额、卡住回收与迟到结果丢弃全部通过。
- 新增用例：名额可重复释放不重复扣减；进行中的检查被判定卡住后返回检测超时、自动重试成功、迟到旧结果不覆盖、名额归零。
- `node --test --no-experimental-webstorage web/tests/cluster-connection-status.test.mjs`：6 项通过，新增“检测中超过窗口改为检测超时并降低轮询频率、手动刷新重新检测”。
- 前端 `vue-tsc --noEmit --skipLibCheck` 通过。

## 边界

- 本机运行中的 `edo-local-api-1`/`edo-local-web-1` 仍是修复前的构建，本次未重启、未重建、未部署；现有卡住条目只存在该进程内存中，需重新构建镜像后才会消失。
- 未修改集群、kubeconfig、主机或任何 Kubernetes 资源；未重写历史状态。

## 现场复核（2026-11-17 21:20）

- 用真实数据库、真实 kubeconfig 和 EDO 自身的连接检查代码（同一 `connectionStatusCache`）在 API 容器网络命名空间中复核：`测试` 集群为 `connected`（检查 2ms 级返回，缓存键稳定命中），`本地集群` 为 `connected`，`ci内网集群` 为 `unreachable/timeout`（该集群地址本身不可达），`测试测试` 为停用。
- 因此页面上的灰点属于前端的"检测超时"兜底结论（当时 API 正在重启且该标签页已转入后台不再轮询），不是后端仍把该集群判成不可用。刷新页面后按真实结果展示为已连接。
