# 仓库轮询触发失败恢复

本批对应 BT-06 的自动代码触发分支。管理员启用流水线及对应事件，使用可控远程引用和各用例独立数据库，不运行真实业务构建或部署。

| 用例 | 前置与操作 | 预期 |
| --- | --- | --- |
| PTR-01 | 已建立基线；新增 Tag；模拟创建运行前读取构建配置失败；解除故障并再次轮询 | 失败时不登记新 Tag 游标，应用显示安全的触发失败提示；下次自动创建并投递一条运行 |
| PTR-02 | 已建立 Tag 或分支基线；移动到新 Commit；模拟创建失败后恢复 | 失败时保留旧 Commit，恢复后使用新 Commit；不改写历史运行 |
| PTR-03 | 已建立基线；新增分支；创建失败后恢复 | 未持久化运行前不消费事件，状态更新时间不会阻止下次触发 |
| PTR-04 | PR 从 opened 变成 merged，Commit 保持相同；创建失败后恢复 | 保留旧动作游标，恢复后识别合并事件，不仅按 Commit 判断 |
| PTR-05 | 新 Tag 创建运行时，模拟运行来源记录写入失败 | 运行事务回滚，游标不前进，无任务或 Outbox 残留，恢复后正常投递 |
| PTR-06 | 上述事件恢复后连续重复轮询 | 只有一条运行；任务和 Outbox 数量不增加 |
| PTR-07 | 当前本机 demo 的 v0.0.5 | 只读核验首次观察与系统日志，确认主机目录读取超时发生在创建运行前；不把自动化夹具冒充这条业务流水线已成功运行 |
| PTR-08 | 创建运行的准备阶段请求超时或取消；使用新请求继续检查 | 有界保存安全失败状态，运行状态更新不冒充配置修改，下次仍能识别新 Tag |

实现继续使用现有 GORM 事务、事件去重键、项目范围与任务投递能力，不增加依赖或改写历史数据。运行成功持久化前不推进候选事件游标；创建失败记录原始诊断与应用、仓库、流水线、Ref、Commit，接口和同步状态仅提供安全中文提示。已登记的运行继续沿用原有失败与去重语义，不自动重跑实际构建或部署失败的任务。

初始复现：PTR-01 至 PTR-04 的五个场景均失败，证明创建失败后仍推进了监听游标。修复后执行结果另行记录，不把复现失败改为通过。

修复后验证：

- PTR-01 至 PTR-06、PTR-08：独立 SQLite 与 MySQL 均通过，使用真实业务查询和事务、注入准备或持久化失败，保留 Go 竞争检测。SQLite 同时完成整个 `internal/pipeline` 包回归；MySQL 定向覆盖轮询、Tag 规范化和 Webhook 去重。临时 MySQL 已清理。
- `go vet ./internal/pipeline` 和差异空白检查通过。
- PTR-07：本机日志确认在 2026-11-13 10:31 检测到 `v0.0.5`，创建运行前读取执行主机用户目录超时；对应游标存在、运行记录不存在。仅只读诊断，未清空监听游标、改写历史或补执行这条业务流水线。
