# 手动 SQL 审计

入口：**基础设施 → SQL 审计**。这是独立的手动工单流程，不会因为合并分支、批准工单或启动发布而自动执行 SQL，也不会自动暂停、继续已有流水线。

## 使用方法

1. 在“应用数据库”保存并测试应用对应的 PostgreSQL 或 MySQL 连接，选择准确环境。数据库凭据加密保存。
2. 管理员在项目角色中分配 SQL 审计权限，并让审核人加入同一项目。
3. 创建 SQL 工单，选择应用、本次流水线运行、分支、目标数据库和审核人，填写 SQL。环境与仓库由实际关联派生，不能跨项目选择。
4. 选择人工执行位置：“发布前”（默认）或“发布后”。此选项用于记录操作安排，当前版本不自动保证与应用部署的先后顺序；操作者应按发布安排点击执行。
5. 保存后后台自动进行静态检查。检查通过后，由指定审核人批准或驳回。申请人和当前 SQL 内容的修改人不能自审。
6. 有执行权限的人查看准确 SQL、目标、本次发布及摘要，确认后点击执行。接口只受理后台任务，关闭页面不会停止任务；再次打开可查看状态。
7. 指定审核人可填写原因后跳过本次 SQL。跳过记录不是数据库执行成功，不影响其他发布或目标库。

每条工单绑定本次发布和一个实际数据库。重复点击、重试 HTTP 请求或消息重投不会再执行同一项。下一次发布需要明确创建新的发布项，不继承上次的跳过。

执行成功后不能修改、删除。尚未成功的工单可以修改，修改会生成新修订，旧批准失效并重新检查、审核。排队和执行中的工单不能修改。失败或中断可能已有部分效果，记录保留为失败或“需要核对”，不能通过任务中心重试，也不会自动执行反向 SQL。

## 角色权限

所有动作都需要 `sql_change.read`，并继续检查项目成员资格、部门隔离、个人显式拒绝及关联资源。

| 权限 | 操作 |
| --- | --- |
| `sql_change.read` | 查看列表、SQL 正文、检查、审核和执行记录 |
| `sql_change.create` | 创建工单并自动检查 |
| `sql_change.update` | 修改未执行成功的工单并重新检查、审核 |
| `sql_change.delete` | 删除未成功、非排队或运行中的工单 |
| `sql_change.check` | 手动重新检查；不继承旧批准 |
| `sql_change.review` | 指定审核人批准或驳回 |
| `sql_change.execute` | 人工发起执行，同时要求 `application_database.execute` |
| `sql_change.skip` | 指定审核人填写原因跳过，同时要求审核权限 |

有审核权限不代表可以审核任意工单。后台执行前及运行中会重新校验权限和数据库版本；撤权或目标变化不会沿用旧授权继续执行。

## 检查能力与限制

- 复用固定版本 `sqlfluff/sqlfluff:4.4.0`，检查 PostgreSQL/MySQL 语法和规范，并在其语法树上识别删除对象、清空表和未设置 WHERE 的更新、删除。风险提示供人工核对，不代表已经完成备份、锁影响分析或目标库验证。
- 仅支持常规表、索引、视图、序列的 DDL，以及查询和数据变更。事务控制、切库、权限修改、函数、存储过程等未支持语句在检查阶段拒绝，不交给执行器尝试。
- 不接受 MySQL/MariaDB 可执行注释和跨数据库对象引用。MySQL 表名不带库名前缀（同库前缀也省略）；PostgreSQL 可以使用当前数据库的 schema 前缀。
- 每项 SQL 最多 16 KiB、100 条语句。不接受自定义 SQLFluff 配置、模板、忽略检查指令或 Goose 控制注释。
- 工具故障、超时、报告缺失、超限或无法解析会阻断，不能算作“没有问题”。静态检查不连接目标数据库，不使用 `EXPLAIN ANALYZE` 或“执行后回滚”冒充试运行。

EDO 需要可用的 Docker CLI 和当前构建运行时。检查使用按需临时容器，不新增常驻扫描服务；容器断网、只读、非特权、无宿主目录挂载和数据库凭据，限 1 CPU、512 MiB 内存、64 个进程，检查总时限 60 秒。首次运行需要拉取工具镜像。Compose 仍使用本实例隔离的 Docker-in-Docker。

## 执行与记录

执行复用现有加密数据库连接和 Goose 3.27，只执行已审定修订。按数据库指纹与已有流水线迁移共享 Redis 锁，同一目标串行，不使用全局锁。

目标数据库中新增 `edo_sql_change_receipts` 和 `edo_sql_change_versions` 两张小型执行账本，执行账户需要创建这两张表及实际变更所需的最小权限。账本保存执行 UUID、摘要和结果，不保存 SQL 正文或密码；不得人工清空账本以重放变更。不同地址若指向同一个实际数据库，应统一使用同一连接配置，不能把域名/IP 别名当成独立目标。

执行账户只授予目标库所需权限，不使用数据库超级用户，也不授予跨库、文件写入、外部连接或系统管理能力。静态解析不能证明用户函数没有副作用；审核人仍须核对函数调用、数据范围和业务影响，这不是任意 SQL 的安全沙箱。

EDO 平台新增工单、修订、审核和执行四张表。SQL 正文和检查报告加密保存；队列消息只携带 UUID，系统日志及操作审计不记录正文、字面值或凭据。升级只增加表和索引，不迁移、执行现有业务 SQL。

MySQL DDL 可能隐式提交，网络中断也可能发生在提交之后。因此，失败或结果不确定时必须核对目标状态；“有执行账本”不等于能够保证任意外部 SQL 的跨数据库事务或自动安全回滚。

## 依赖选择

本版本复用现有 SQLFluff（MIT）和 Goose（MIT），SQL 编辑器使用官方 CodeMirror SQL 方言包（MIT），不增加常驻组件或新的后端数据库解析依赖。SQLFluff 的安全边界参见[官方安全说明](https://docs.sqlfluff.com/en/stable/usage/security/)，执行器能力参见 [Goose](https://github.com/pressly/goose)。

评估过 Bytebase 完整平台、MySQL 专用 goInception、TiDB parser 和 PostgreSQL 专用 pg_query_go；它们分别存在整套平台及许可证边界、GPL-3.0/单方言、单方言及依赖规模、CGO/单方言等引入成本。本版本的业务范围不需要引入这些依赖。EDO 自身只维护工单、审批、权限、执行范围和基于解析树的少量风险规则；这些规则不是完整数据库审计引擎，后续扩大语法支持必须增加真实方言语料和执行回归，不能退回正则判断安全。
